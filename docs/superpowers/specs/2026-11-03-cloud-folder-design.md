# 雲端資料夾與顧問交付檔案

日期：2026-11-03
狀態：設計，待使用者確認

## 1. 為什麼要做

使用者在本機跑 etfflow 時，每週會拿到一份可以直接交付的週報：`.docx` 裡有文字，也嵌了四張排行長條圖（前十大流入／流出、報酬率前十／後十），另有一份 `.md`（例：`D:\code\etfflow_article\weekly_report\output\output_2026-W43\humanized\`）。

平台上的 ETF 顧問也會寫週報，但成品只是一則 markdown 訊息：沒有圖，也沒有檔案。使用者要交付就得自己複製、排版。

使用者要的是：在平台上請顧問做事，拿到跟本機一樣、能直接交付的檔案，而且有一個「雲端資料夾」可以看到、管理自己的檔案。

檔案流向的現況：

- 使用者上傳 → storage `project-files/<專案id>/<檔名>`（只有一層）→ 每次 run 前 runtime 同步到 Sprite 的 `/workspace/shared`，所有顧問與主管都讀得到（`packages/runtime/src/sync.ts`）。
- 反方向不存在：顧問寫的檔案只留在 Sprite，使用者看不到也拿不到。
- 專案頁側欄的「專案資料」（`apps/web/components/workspace/file-panel.tsx`）只能上傳、列出，不能下載。

## 2. 目標

1. **顧問可以交付檔案。** 平台給所有顧問一個「交付檔案」工具。只有經過這一步的檔案才會出現在使用者的雲端資料夾，暫存檔、腳本、中間資料都留在顧問自己的工作目錄。
2. **對話裡直接下載。** 顧問交付檔案的那則回覆出現下載按鈕。
3. **專案資料夾（側欄，草圖 A）。** 專案頁側欄的「專案資料」改成資料夾檢視：使用者上傳的檔案，加上每位顧問交付的檔案。
4. **我的雲端（帳號層級，草圖 C）。** 導覽列多一個「我的雲端」入口，跨專案集中看所有檔案，每個專案一個資料夾，裡面的結構跟 3 一樣。
5. **完整管理。** 3 和 4 兩個入口都能看、下載、上傳、刪除、改名、搬移、新增資料夾。兩邊看的是同一批檔案。
6. **顧問讀得到雲端資料夾的檔案。** 雲端資料夾就是 `/workspace/shared` 在使用者這一端的對應：使用者上傳的和顧問交付的檔案，都同步到 `/shared`，保持同樣的資料夾結構。使用者在雲端改名、搬移或刪除後，下一次 run 前 `/shared` 會跟著更新。
7. **ETF 顧問交付跟本機一樣的週報**（第 6 節，改的是 fintech repo）。

## 3. 不做的事

- 匯出對話：另一個獨立功能（見待辦），這次不做。
- 線上預覽、線上編輯 docx。
- 資源回收筒、檔案版本歷史。刪了就沒了（我決定：先從簡；使用者之後要再加）。
- 整個資料夾打包成 zip 下載（我決定：先一個檔案一個檔案下載）。
- 跨專案分享檔案給別的使用者。
- 顧問之間的新隔離規則：`/shared` 本來就是所有顧問共用的交接區（`docs/security-model.md` 第 3 節），交付的檔案讓所有顧問讀得到，暴露範圍沒有比現在大。

### 做壞了也算失敗的情況

- 舊回覆裡的下載按鈕，在使用者改名或搬移檔案後失效。
- 使用者在「我的雲端」看到別人的檔案，或顧問能把檔案交付到別的專案。
- 顧問的暫存檔大量出現在雲端資料夾。
- 刪除專案後，檔案還留在 storage（現在就是這樣，見 4.6）。

## 4. 平台設計（eric-agenthub）

### 4.1 檔案要有身分

下載按鈕要能跟著檔案走，不能只靠 storage 路徑，所以新增資料表記錄每個檔案（我決定）。欄位方向：

- `id`（uuid）、`project_id`、`folder`（資料夾路徑）、`name`（顯示檔名）、`size`、`content_type`、`storage_path`、`created_at`、`updated_at`
- 來源：`source`（`user` 或 `agent`）、`agent_instance_id`（顧問交付時）、`message_id` 或 `run_id`（在哪一則回覆交付）
- 刪除：直接刪列並刪 storage 物件；舊回覆查不到檔案時，按鈕顯示「檔案已刪除」

storage 路徑跟顯示用的資料夾、檔名脫鉤（例如 `project-files/<專案id>/<檔案id>`），所以改名、搬移只改資料表，不搬 storage 物件（我決定）。

既有的上傳檔案（目前在 `project-files/<專案id>/<檔名>`）要搬進新制，或替它們補資料表紀錄。做法交給實作者，但正式站上既有專案的檔案不能消失，顧問照樣讀得到。

### 4.2 資料夾結構

- 預設有「我上傳的」，加入專案的每位顧問各一個資料夾，以顧問名稱命名，例如「ETF 資金流顧問」。
- 顧問交付時可以指定子資料夾，例如 `2026-W43`。
- 使用者可以自己開資料夾，也可以把任何檔案（含顧問交付的）搬到任何資料夾。
- 同一資料夾裡同名時不覆蓋，自動加序號，例如 `週報 (2).docx`（我決定）。顧問重跑同一週也會保留前一版。
- 使用者可以開空資料夾，所以資料夾本身也要有紀錄，不能只靠檔案路徑推出來。
- 顧問只能交付到自己的資料夾底下（我決定），不能放進「我上傳的」或使用者開的資料夾。使用者把顧問資料夾改名或刪掉後，顧問下次交付會重新建一個原名的資料夾。
- 顧問被移出專案時，它的資料夾和檔案保留（我決定：檔案是使用者的）。

### 4.3 交付工具（runtime）

- 新工具，名稱交給實作者（例如 `deliver_file`），所有顧問都有，主管不需要（我決定：成品由顧問產出；主管要彙整成檔再議）。
- 參數：工作目錄或 `/shared` 裡的檔案路徑、選填的子資料夾、選填的顯示檔名。
- 以該顧問的沙盒帳號讀檔，權限跟 `read_file` 一樣：讀不到的檔案就交不出去，symlink 指向的檔案也一樣。
- 上傳時檢查大小。上限交給實作者，建議單檔 50 MB，同一次 run 有總量上限。
- runtime 現在對 `project-files` 只有讀取權限（migration `20261014000002` 的 `runtime_read_project_files`）。要讓交付能寫入，可以替 runtime 帳號開「只能新增到自己專案、不能改刪」的寫入權限，也可以走 Vercel 的 API（類似 `/api/runtime/model`）。由實作者選，選完更新 `docs/security-model.md`。原則：runtime 只能新增檔案到自己的專案，不能刪改使用者的檔案。
- 平台的顧問通用規則加一句：做出要給使用者的檔案（報告、圖表、表格）時，用交付工具交付；暫存檔不要交付。

### 4.4 對話裡的下載按鈕

- 交付成功後，該則回覆顯示檔案卡片：檔名、大小、下載按鈕。
- 多位顧問協作時，卡片出現在該顧問的派工卡片或討論發言裡。主管的最終回覆底下也列出這次 run 交付的所有檔案（我決定：使用者最常看的是主管的最終回覆）。
- 瀏覽器目前只收到工具摘要，不收原始輸入輸出（`docs/security-model.md` 第 3 節）。卡片需要的檔案 id、檔名、大小要另外送，不要因此放寬摘要規則。
- 下載用短效簽章連結，每次按才產生，只發給專案擁有者。

### 4.5 同步到 `/shared`

- 現在的 `syncSharedFiles` 只同步第一層、以檔名為準。要改成依資料表同步完整的資料夾結構，例如 `/workspace/shared/ETF 資金流顧問/2026-W43/週報.docx`。
- 使用者改名、搬移、刪除後，下一次 run 前同步。舊路徑的檔案要清掉，但只清以前同步下來的；顧問自己直接寫進 `/shared`、沒有交付的檔案不受影響（跟現在一樣）。
- 中文檔名、資料夾名要能用。現在的 `storageFileName` 會把非英數字元換成 `_`，因為 storage 路徑的限制；改成路徑用 id 之後，顯示名稱可以保留中文。
- `read_file` 看圖片的條件是「共用資料夾第一層、跟上傳版本相同」（`packages/runtime/src/tools/files.ts` 的 `sharedName`、`images.ts`），要跟著改成支援子資料夾。
- 顧問 prompt 裡列出的共用檔案清單（`prompts.ts` 的 `filesSection`），檔案多時要有上限或改成列資料夾，避免灌爆 prompt。

### 4.6 刪除專案

現在 `DELETE /api/projects/[id]` 只刪 Sprite、runtime 帳號和資料庫列，storage 裡的檔案沒刪，但確認訊息寫「對話、記憶和資料都會一起刪除」。這次一併補上：刪專案時刪掉該專案所有 storage 物件，「我的雲端」裡該專案的資料夾也跟著消失。

### 4.7 畫面

**專案頁側欄（A）**：取代現在的 `FilePanel`。資料夾樹狀列表，每個檔案可以下載，有刪除、改名、搬移、新增資料夾，上傳照舊。手機上在現有的底部面板裡。

**我的雲端（C）**：導覽列新入口、新頁面。第一層是使用者的所有專案，點進去就是該專案的資料夾，操作跟 A 相同。上傳時要在某個專案資料夾裡（我決定：檔案一定屬於某個專案，顧問才讀得到）。

刪除要先確認。畫面細節交給實作者，沿用現有的元件與樣式（`panel`、`btn`、`notice`、`BottomSheet`）。

草圖：`.superpowers/brainstorm/2258-1793711722/content/cloud-folder.html`（使用者選 A＋C）。

### 4.8 權限

- 所有檔案操作都只限專案擁有者（`getOwnProject`）。「我的雲端」只列自己的專案。
- 新資料表照 1-C 的規則：一般使用者與匿名沒有權限，網站用 service role；runtime 只能讀自己專案的列，交付只能新增。
- 更新 `docs/security-model.md`：第 3 節的表格（租用者看得到的 `/shared` 內容）、權限表、交付寫入的路徑。

## 5. 驗收

- 單元與整合測試照現有慣例（Vitest、會連真的 Supabase；runtime 測試從 Git Bash 跑）。
- 正式站 e2e（臨時帳號開專案、租 ETF 顧問）：請顧問寫週報 → 回覆出現下載按鈕 → 下載到的 docx 打得開、有圖 → 側欄與我的雲端都看得到 → 改名、搬移後舊按鈕仍能下載 → 刪除後按鈕顯示已刪除 → 另開對話請投組顧問讀那份週報，讀得到 → 刪專案後 storage 沒有殘留。
- runtime 有改，要 publish-runtime 並 redeploy 所有 Sprite（要先跟使用者確認）。有 migration，由使用者在 Dashboard 套用。

## 6. ETF 顧問交付週報（agenthub-fintech-agents）

平台功能上線後才做，改的是 fintech repo 的 skill 與 requirements，不改平台。

- 週報寫完、檢查完數字後，在沙盒裡產生跟本機一樣的成品：一份 `.md`、一份 `.docx`，docx 嵌入四張排行長條圖。版面參考 etfflow 的 `weekly_report/stages/stage4_tw_assembly.py` 和 `weekly_report/images/` 的圖。
- 用交付工具交付 docx、md 和四張圖，子資料夾用週次（例如 `2026-W43`）。
- 只交最終版，不交本機那種 `qa_fixed/`、`humanized/` 中間稿。
- 需要的套件（例如 `python-docx`、`matplotlib`）寫進 ETF 顧問的 `requirements.txt`。
- 改完照既有流程 `scripts/pack.py` → `scripts/publish_agents.py` 重新上架；已加入專案的是快照，要開新專案才會用新版。
