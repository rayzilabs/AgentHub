# 組織：團隊內部共用顧問

日期：2026-11-09
狀態：設計草稿，已過 builder check，待使用者審閱

## 1. 為什麼要做

使用者自己的實驗室（教授與學生）想在內部共用一批金融顧問，但不想放到公開市集：這些顧問可能用到實驗室自己的資料、或還沒發表的研究方法。之後別的公司也會有一樣的需求。

成員會一直換（學生入學、畢業；公司員工到職、離職），所以做成**組織**：顧問設定成「這個組織的人能用」，換人只改成員名單，不用一個個顧問去改可以用的人。

第一個使用者是這個實驗室；做法要能直接套用到公司。

## 2. 目標

- 任何登入使用者都能建立組織、邀請成員、管理成員。
- 顧問範本可以只放在某個組織裡：只有該組織成員看得到、租得到，不出現在公開市集。
- 成員離開組織後，他專案裡的組織顧問不能再呼叫。
- 顧問屬於組織：做顧問的人離開，顧問仍在，其他成員照樣能用。

## 3. 不做的事

- **多人在同一個專案裡協作**（共用對話、檔案）：另一個待辦，不限於組織，不在這次範圍。專案仍只有一位擁有者。
- **寄邀請信**：平台現在完全不寄信，正式站也沒有自己的網域。這次邀請用 email 指定對象但不寄信；真的寄信（附一次性連結）是之後的待辦。
- **註冊流程優化**（例如 email 驗證）：另一個待辦。
- 金流、計費、組織的用量統計。
- 比「管理員／一般成員」更細的角色。
- 組織層級的共用雲端資料夾或共用記憶。

## 4. 失敗的情況（就算功能能跑也算失敗）

- 組織顧問的名稱、說明、skill 內容被組織外的人看到，或出現在公開市集、公開 API 回應裡。
- 離開（或被移出）的成員還能透過舊專案呼叫組織顧問，包括主管派工、討論、遠端 MCP。
- 做顧問的學生畢業後，顧問跟著消失，或沒人能再維護。

## 5. 使用者決定的事

### 5.1 成員

- 角色只有兩種：**管理員**、**一般成員**。建立組織的人是第一位管理員。
- 一個人可以同時屬於好幾個組織。
- 任何成員都可以邀請別人；被邀請的人要經管理員核准才算加入。
- 離開有兩種：本人自己退出，或被管理員移出。

### 5.2 邀請

- 邀請人輸入對方的 email。平台不寄信，邀請人自己用 LINE 等方式通知對方。
- 對方用這個 email 註冊或登入後，在平台上看到邀請（登入後有提示）。
- 對方先「接受」，才進入管理員的待核准名單；管理員核准後正式加入。這樣管理員名單上只會出現真的想加入的人。
- 管理員發出的邀請，對方接受後直接加入，不用再核准。
- 邀請 7 天有效，過期要重發；發出的人或管理員可以撤回還沒處理的邀請。
- 已知風險：平台不驗證 email 是否為本人的，有人搶先用某學生的 email 註冊就能看到邀請。由管理員核准把關（看到不認識的人就不核准）；管理員發出的邀請沒有這道關卡，這是接受的風險，等寄信版的一次性連結再補上。

### 5.3 組織的顧問

- 一個顧問範本要嘛是公開的、要嘛屬於某一個組織，不能同時是。組織想公開某個顧問，就另外上架一份到公開市集。
- 組織有一個設定「成員放顧問進組織要不要管理員核准」，建立時可設定，預設**不用核准**；管理員之後可以改。
- 組織顧問算組織的。做的人還在組織時，本人與管理員都能修改、下架；做的人離開後，只有管理員能修改、下架。
- 租用流程跟現在一樣：在自己的專案裡選顧問，除了公開市集多一個「我的組織」可以挑（只列出自己所屬組織的顧問）。
- 組織顧問被下架後，已經租進專案的副本也不能呼叫，跟成員離開一樣處理。
- 一般成員看組織顧問跟看市集一樣，只看得到公開欄位（名稱、說明、分類、skill 名稱等），看不到 system prompt、skill 內容與 MCP 設定。只有做顧問的人（仍是成員時）和管理員能看完整內容、能修改。
- 「要核准」的設定只管顧問**第一次**放進組織；核准後的修改不用再核准。
- 管理員能改組織顧問的**全部內容**，包括 system prompt、skill、MCP 網址、平台代管 MCP 的版本與金鑰。學生畢業前要交接的伺服器、金鑰由組織自己處理，平台不負責。
- 已經公開上架的顧問**不能**直接改成組織專用（會讓組織外的既有租用者立刻不能用），要在組織裡另建一個新的；反方向亦同。這次不做「複製範本」功能。

### 5.3a 我決定的（使用者同意了這些建議，但不是使用者提出的）

- 「下架」＝退回草稿，之後可以再上架；不是刪除。
- 能不能呼叫在**每次執行時**即時判斷「專案擁有者現在是不是該組織成員、範本現在是不是上架中」。所以成員重新加入、或顧問重新上架後，舊專案裡的副本恢復可用（跑的是租用當時的快照，跟公開市集的副本一樣）。副本上要自己記得屬於哪個組織，不能只靠 `template_id`（範本被刪時會變成 null）。
- （我決定）組織範本被下架（退回草稿）後再上架，如果組織要求核准就要重新走核准；否則成員可以立刻把管理員剛下架的顧問再上架。
- 做顧問的人離開組織後，對這個顧問就跟組織外的人一樣，看不到完整內容；`getTemplate` 現在「`creator_id` 本人一律回完整資料」的規則對組織顧問要改成看成員身分。

### 5.4 離開之後

- 成員離開組織後，他所有專案裡屬於這個組織的顧問都不能再呼叫。
- 他跟這些顧問過去的對話紀錄、顧問交付的檔案留給他自己，照樣看得到。
- 專案裡其他顧問（公開的、或其他他仍屬於的組織的）照常使用。

### 5.5 畫面

- 導覽列多一個「組織」入口：成員名單、待核准名單、邀請、設定、組織的顧問。
- 被邀請的人登入後看到待處理邀請的提示。

## 6. 現況與限制（實作要知道的）

- `agent_templates.status` 只有 `draft`／`published`，`published` 就是全平台可見（`listPublishedTemplates`、`getTemplate`、`hire_agent` 都只看 `status = 'published'`）。這三處都要改成同時考慮組織歸屬，任何一處漏掉就是第 4 節的失敗。
- 範本的所有操作（`templates.ts`、`hosted-mcp.ts`、`/api/templates/*`）現在都靠 `getOwnTemplate` 比對 `creator_id` 把關；組織顧問要改成「本人（仍是成員）或管理員」，代管 MCP 的部署、發布、下架、換金鑰也包括在內。
- 目前平台沒有「下架」功能，也不能把顧問從專案移除；下架要新做。
- `projects` 只有 `owner_id`，平台沒有任何群組／成員資料表；權限一律寫在 `lib/services/*`，以 `user.id` 比對。資料表開 RLS、沒有給網站使用者的 policy，網站一律用 `adminDb()`。
- **租用是快照**：`hire_agent` 把範本的 system prompt、skill zip 路徑、MCP 設定複製進 `agent_instances`，之後範本變動不影響已租的副本；skill 檔案也已裝在專案的 Sprite 上。所以「不能再呼叫」必須在**執行時**判斷（每次 run、派工、討論、遠端 MCP 閘道 `/api/mcp/<instanceId>/<name>`），不能只靠「租不到」。runtime 由 RLS `runtime_project()` 讀自己專案的 `agent_instances`；要讓 runtime 多一項資料庫權限，照 CLAUDE.md 的規則先改 `docs/security-model.md` 第 4 節，再寫 migration，並在 `supabase/tests/runtime_access.sql` 加斷言。
- migration 由使用者在 Supabase Dashboard 的 SQL Editor 套用（CLI 沒有這個專案的權限）。
- 已知缺口：單一顧問專案會把原始工具輸入輸出串流到瀏覽器（`docs/security-model.md` 第 3 節）。這次不修，但組織顧問一樣受影響，文件要提到。

## 7. 留給實作者決定

- 資料表設計（組織、成員、邀請、範本的組織欄位與待核准狀態）與 RPC。
- 「不能再呼叫」在哪一層擋（Vercel 轉送前、runtime 載入顧問時、兩者都擋），以及執行中的 run 是否中斷——只要滿足：離開或下架之後開始的 run、派工、討論、MCP 呼叫都呼叫不到。被擋的顧問在專案畫面上要看得出「已無法使用」及原因。
- 被擋的顧問留在 Sprite 上的 skill 檔案要不要清掉。
- 最後一位管理員要離開時怎麼處理（例如必須先指定另一位管理員）、要不要能刪除組織。
- 畫面細節與路由命名。
- 測試方式；正式站 e2e 照既有慣例用臨時 `@test.local` 帳號，結束全刪。
