# 顧問各自的 Python 套件（skill zip 裡的 requirements.txt）設計

日期：2026-10-30

## 為什麼要做

2026-10-30 正式站一批使用者（約 24 人／小時）大量請顧問自己寫程式計算；當時沙盒的 Python 壞了（見 `docs/security-model.md`「語言工具」），顧問要花好幾輪找 Python、裝套件。語言工具已在佈建時修好、numpy 與 pandas 也預裝，但**不同顧問需要的套件不同**（金融顧問要 numpy、pandas，別的顧問可能要 scipy、yfinance、statsmodels）。平台統一預裝無法涵蓋，讓顧問每次對話自己 `pip install` 又慢又不可靠，創作者也無法事先保證「我的顧問需要的東西都在」。

## 使用者定下的決定

1. 創作者在 **skill zip 裡放 `requirements.txt`**（Python 標準格式），和 `SKILL.md` 放在同一個 skill 資料夾。
2. **每位顧問各自一套環境**：A 顧問的套件版本不影響 B 顧問。
3. **租用後、第一次對話前裝好**：runtime 每次對話開始本來就同步顧問的 skill；`requirements.txt` 有變動才重裝，平常不重複安裝。
4. 顧問執行 Python 時，自動用自己的那一套環境。
5. **上架時輕量檢查**：格式正確、每個套件名稱在 PyPI 存在、指定的版本也存在；有錯就在上架頁面顯示錯誤、不能發布。不實際安裝。
6. **真正安裝仍失敗時**：顧問照樣能對話，但會被告知「套件 X 安裝失敗」，不假裝套件存在；使用者也看得到警告。

## 目標

- 上架（上傳 skill zip、處理上傳 `process_upload`、發布）時檢查 zip 裡所有 `requirements.txt`：
  - 每行只能是「套件名稱（可含 `[extras]`）＋可選的版本條件（`==`、`>=`、`<=`、`~=`、`!=`、`<`、`>`，可多個以逗號分隔）」、空行或 `#` 註解。
  - 拒絕：以 `-` 開頭的選項（`-r`、`-e`、`--index-url`…）、URL、`@` 直接參照、本機路徑、環境標記（`;`）。理由：只允許從 PyPI 安裝具名套件，避免指向任意來源。（我的決定）
  - 每個名稱查 PyPI JSON API（`https://pypi.org/pypi/<名稱>/json`）確認存在；有 `==` 的版本要在該套件的 releases 裡。
  - 上限：每份 50 行、整份 4 KB。（我的決定）
  - 錯誤訊息列出哪個 skill、第幾行、什麼問題，沿用既有 `SkillZipError` 的呈現方式。
- 一位顧問有多個 skill、各有 `requirements.txt` 時，安裝時合併成一份（照 skill 名稱排序串接），衝突交給 pip 判斷，失敗就走「安裝失敗」流程。
- runtime 每次 run 準備顧問時（`syncSkills` 之後、建立 agent 之前）：
  - 算合併後內容的雜湊；與上次成功安裝的雜湊相同就跳過。
  - 不同就以**該顧問的沙盒帳號**建立（或重建）虛擬環境並安裝：`python3 -m venv --system-site-packages <顧問環境目錄>`（`--system-site-packages` 讓預裝的 numpy、pandas 照樣看得到）＋`pip install -r`。逾時 5 分鐘。（我的決定）
  - 成功記下雜湊；失敗記下錯誤摘要（不重試到下次 `requirements.txt` 變動或下次 run）。
- 顧問的沙盒執行 Python 時用自己的虛擬環境：該顧問的 `bash`、stdio MCP 的 PATH 前面加上 `<顧問環境目錄>/bin`。主管不受影響。
- 安裝失敗時：
  - 顧問的指示加上一段「以下套件安裝失敗：…（原因摘要）；不要假設它們存在，必要時告知使用者」。
  - 對話串流送出 `data-warning`（沿用 MCP 啟動失敗的既有機制），使用者在對話裡看得到「顧問 X 的套件安裝失敗」。
- 安裝中：第一次對話若需要安裝，前端進度顯示「正在為顧問安裝套件」（沿用既有的進度訊息機制，實作時確認可行做法）。

## 不做的事

- Node／npm 套件（`package.json`）：先只做 Python。（我的決定）
- 在上架時真的安裝一次（要開臨時 Sprite、花一兩分鐘）。
- 套件黑名單（例如禁止 torch）：交給記憶體上限（cgroup 6 GiB）與安裝逾時處理；DATA.md 類文件提醒創作者別用大型套件。
- 跨專案共用已安裝的套件快取。

## 失敗的樣子

- 創作者打錯套件名稱，卻能發布，等到使用者對話才發現。
- 一位顧問的套件改壞另一位顧問的環境，或主管的環境。
- 每次對話都重新安裝，讓第一句回覆前多等幾分鐘。
- 安裝失敗但顧問照樣寫出「已用 X 套件計算」的內容。
- `requirements.txt` 被拿來指向 PyPI 以外的來源。

## 限制

- 平台在 Eric 的 repo，main 開發、push 自動部署 web；runtime 要 `publish-runtime`＋`redeploy-runtime`。
- 沙盒帳號與目錄規則見 `docs/security-model.md` 第 5 節；新增的環境目錄要寫進那裡的目錄表（擁有者、權限）。
- 安裝在 run 的 15 分鐘預算之內（顧問 11 分鐘開始收尾）；5 分鐘逾時要保留足夠時間給對話本身。
- 上架檢查在 Vercel 執行，需要連 PyPI；PyPI 暫時連不上時的處理（擋下或放行並標示「未驗證」）留給實作者，傾向擋下並請創作者稍後再試。

## 留給實作者

- 顧問環境目錄的位置與權限（例如 `/workspace/envs/<顧問 id>`，擁有者為該顧問的沙盒帳號；或放在顧問工作目錄底下的隱藏資料夾）。
- 雜湊與失敗紀錄存哪裡（環境目錄裡的檔案即可，不必進資料庫）。
- PyPI 查詢的平行度與逾時、名稱正規化（PEP 503：大小寫、`-`／`_`／`.` 視為相同）。
- 版本條件解析用現成的套件或自寫最小解析器。

## 驗收

- 上架：含錯字套件、不存在的版本、`-e git+…`、URL 的 `requirements.txt` 都被擋下並指出行號；正確的可以發布。
- 真實 Sprite：兩位顧問各自宣告不同版本的同一套件（例如 `requests==2.31.0` 與 `requests==2.32.3`），各自 `python3 -c "import requests; print(requests.__version__)"` 印出自己的版本；numpy、pandas 兩位都能 import；第二次對話不重新安裝。
- 安裝失敗（宣告一個在 PyPI 存在但在 Linux 上編譯不起來的套件）：對話照常完成，顧問的回覆提到安裝失敗，對話裡出現警告。
